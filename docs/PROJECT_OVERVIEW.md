# 소비데이터를 활용한 점검 우선순위 분석 기획

BC카드 소비데이터 활용 공모전을 준비하며, 소비의 변화를 여신·리스크 담당자의
추가 점검에 어떻게 연결할 수 있을지 탐색한 프로젝트입니다.
이 페이지는 프로젝트의 목적과 접근 방식, 본인 역할을 소개합니다.
대회 제출 완료나 수상, 금융기관 도입 실적을 의미하지 않습니다.

## 무엇을 하려 했는가

처음의 질문은 “소비 흐름이 약해지는 곳을 찾아, 담당자가 먼저 확인할 대상을
정리할 수 있을까?”였습니다. 단순히 매출이 감소한 곳을 나열하기보다,
어떤 변화가 나타났고 무엇을 더 확인해야 하는지 설명하고자 했습니다.

여신전략·신용정책·리스크기획·리스크관리 관점에서 관심을 둔 것은 자동 대출
결정이 아니라, 제한된 정보를 판단에 연결할 때 필요한 기준과 주의사항입니다.

## 왜 분석 범위를 좁혔는가

초기에는 소비 변화를 여신 위험과 연결하는 넓은 구상을 검토했습니다.
그러나 소비 변화만으로 개별 사업자의 상환능력이나 부실을 단정할 수는 없습니다.
그래서 목표를 부실 예측이나 자동 한도 산정이 아닌, 추가 점검을 지원하는 분석으로
좁혔습니다. 데이터로 확인할 수 있는 내용과 별도 정보가 필요한 판단을 구분하는 것이
이 프로젝트의 중요한 기준이었습니다.

## 어떤 순서로 접근했는가

### 먼저 자료의 의미와 비교 가능성을 확인

지표를 만들기 전에 한 행과 각 항목이 무엇을 뜻하는지 확인하는 절차를 두었습니다.
기간 누락이나 중복이 있다면 실제 변화와 자료의 문제를 혼동할 수 있기 때문입니다.
거래가 적은 대상을 같은 기준으로 해석해도 되는지도 검토 대상으로 두었습니다.

### 한 가지 숫자보다 변화의 양상을 확인

소비 규모와 거래 빈도를 구분하고, 특정 시점의 변화뿐 아니라 기간 중 흐름도
살펴보는 방향으로 분석을 구성했습니다. 하나의 지표가 좋아 보인다는 이유만으로
전체 상황이 양호하다고 판단하지 않기 위해서였습니다.

### 비교 기준과 판단의 한계를 함께 검토

단순 증감만으로 결론을 내리지 않고, 비교 대상의 흐름에 따라 해석이 달라질 수 있다는
점을 고려했습니다. 또한 기준을 바꾸었을 때 판단이 유지되는지 확인하는 절차를
포함했습니다. 복잡한 방법 자체보다 결과를 이해하고 설명할 수 있는지를 우선했습니다.

### 분석 결과와 실제 여신 조치를 구분

분석이 제공하려는 것은 추가 확인의 출발점입니다. 소비 약화 신호를 곧바로
대출 한도 축소나 부실 판정으로 연결하는 것은 범위에서 제외했습니다.
실제 여신 판단에는 별도의 차주 정보와 검증이 필요하다는 경계를 유지했습니다.

## 본인 역할과 AI 활용

본인은 여신·리스크 직무 관점의 활용 목적을 정하고, 설명하기 어려운 과장된 주장을
제외하도록 요청했으며, 결과만이 아니라 분석 과정과 선택 이유가 드러나도록 방향을
조정했습니다.

코드 작성·실행과 검증 문서 초안 작성에는 AI의 지원을 받았습니다. 이를 모두 직접
개발한 경험으로 소개하지 않습니다. 직접 계산을 검토하거나 수정한 경험은 본인이
확인한 범위에 한해서 별도로 설명합니다.

## 이 경험에서 설명하고 싶은 점

복잡한 모델을 사용했다는 사실보다, 문제를 데이터로 확인 가능한 질문으로 좁히고,
판단의 근거와 한계를 함께 설명하려 했다는 점입니다. 여신·리스크 업무에서도
관측된 변화와 추가로 확인해야 할 사항을 구분하는 태도로 연결하고자 합니다.

## 함께 읽을 자료

이 문서는 프로젝트의 목적과 접근 방식을 소개합니다. 실제 자료에서 계산한 요약 통계와
판단 과정은 [분석 과정](ANALYSIS_STORY.md)에 정리했습니다. 원본 데이터와 상세 결과표,
발표자료는 이 저장소에 포함하지 않습니다.

[저장소 안내와 실행 방법](../README.md)에서 가상데이터 코드 예제를 실행할 수 있습니다.
가상 예제는 처리 흐름을 설명하며 실제 분석 결과를 재현하거나 예측력을 검증하지 않습니다.

공개 코드는 핵심 계산과 가상 실행에 초점을 둡니다. 본문에서 설명한 전체 품질점검,
가중치별 비교와 실제 결과 검증 중 일부는 로컬 작업이며 공개 예제에는 포함하지 않았습니다.
[분석 과정](ANALYSIS_STORY.md)의 각 주석에서 공개 코드로 확인할 범위를 구분했습니다.
비공개 자료가 있다는 사실이 검증되지 않은 기능이나 성과를 입증하는 것은 아닙니다.
